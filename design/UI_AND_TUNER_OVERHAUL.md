# Cadence UI and tuner overhaul proposal

Status: implementation candidate. The standalone [tuner prototype](tuner-prototype.html) remains disposable HTML/CSS with a small timed animation script; the production tuner now follows this design. Physical guitar and Safari validation remain open.

## Direction

Keep the practice screen's quiet, full-viewport design. The tuner uses the same color, typography, spacing, icon, focus, and motion rules. On a phone, strings run vertically and their notes sit at the bottom; on tablet/desktop, strings run horizontally with notes beside them. One chevron beside the group of notes opens the **tuning preset** list and changes all six target notes together. The prototype places it on the right on phones and below the rows on larger screens. Chromatic mode keeps a vertical needle that turns around a fixed pivot at every size; only the detected note and guidance move from above it on phones to its left on tablet/desktop. Pitch marks sit above the needle and chromatic note names below. String animation bends only the string, never the note label. Chromatic mode does not ask for a target string. Both modes keep microphone state visible and reserve warning UI for a confirmed state.

The preset list must be keyboard/touch accessible, identify the active preset, and contain the nine current presets: Standard, Drop D, Half Step Down, Full Step Down, Drop C, DADGAD, Open D, Open G, and Open E. A selected string changes by tapping its note/string; selecting a preset changes every target in one transaction. Settings and theme keep their existing behavior. Reduced-motion and safe-area layout remain first-class.

The prototype's string motion is a slowed visual analogy: both ends stay fixed, the middle oscillates transversely and decays. The rate changes with each target pitch, including alternate tunings, but cannot literally show 65–330 Hz string cycles on a display that commonly refreshes around 60 Hz. Stroke widths follow the relative gauges of a representative 10–46 electric set; real users' string sets vary. These choices follow [Penn State's fixed-end plucked-string model](https://www.acs.psu.edu/drussell/Demos/Pluck-Fourier/Pluck-Fourier.html), [Ernie Ball's published 10–46 gauges](https://ca.ernieball.com/guitar-strings/electric-guitar-strings/slinky-classic-rock-n-roll-pure-nickel-wrap-electric-guitar-strings), and [MDN's refresh-rate explanation](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame).

## Design system and package ownership

Use Tailwind CSS v4 for layout and composable utilities, with shadcn/ui as **owned component source** rather than a runtime UI dependency. Start with a Cadence theme preset/registry entry that records semantic tokens, radii, type scale, spacing, and component variants. Keep that preset versioned in the public repo so the design can be reproduced; do not run a generator over existing files wholesale. The prototype's values are exploratory and should be reconciled with the current light/dark tokens.

Map existing colors to semantic roles: `background`, `foreground`, `surface/card`, `primary`, `primary-foreground`, `muted`, `border`, `destructive`, `success`, and `focus`. Define light and dark values once in `@cadence/ui`, expose them through Tailwind's `@theme inline`, and keep focus, hover, disabled, contrast, reduced-motion, and touch target rules alongside the tokens. Avoid page-specific hard-coded colors.

Create public primitives for Button/IconButton, Field/Input, Select/Popover, Dialog/Sheet, Tabs/SegmentedControl, Tooltip, and status messages, then compositions for the practice toolbar, chord timeline, settings sections, tuner controls, and responsive tuner stage. Custom SVG/CSS stays for dynamic fret/string geometry and animated meter elements; Tailwind does not need to replace every authored rule. Compose cloud auth, onboarding, pricing, account, and subscription flows from these public primitives, with only hosted-specific layouts and styles in `@cadence-cloud/ui`. Clerk, Stripe, billing, and entitlements stay private. The public self-hosted app remains account-free.

Migration sequence: inventory repeated controls and screenshots; land tokens/primitives and a visual baseline; migrate public practice/settings/tuner one composition at a time; release a versioned `@cadence/ui` tarball; migrate cloud screens against that release; then remove obsolete selectors. Verify both light/dark themes at phone, tablet, and desktop widths. Watch CSS bundle output and missing utility classes in the private app's packed-package build.

## Tuner detection and warning behavior

The current 2048-sample time-domain frame is about 43 ms at 48 kHz, roughly 3.5 cycles at low E2. Longer low-note context, overlapping windows, and confidence handling should be evaluated before choosing a Rust algorithm. Candidate estimators are [YIN](https://iro.umontreal.ca/~pift6080/H09/documents/papers/yin_pitch_tracker.pdf) and the [McLeod pitch method](https://citeseerx.ist.psu.edu/document?doi=60dd4c01f687858a5fbf6c021920c56247bcf2db&repid=rep1&type=pdf); compare them on actual guitar attacks, harmonics, noisy input, altered tunings, and low E/Drop C. Neither is assumed to be better until evaluated.

The Rust tuner API should emit `frequency`, `confidence`, sample timestamp, and signal level. It should suppress weak/ambiguous frames and octave jumps. A Rust state machine should require agreement over contiguous processed sample time before confirming a note, apply hysteresis around the ±3-cent in-tune boundary, and briefly hold the last stable reading through a pluck's decay. During acquisition, show a calm listening state, not a wrong-note or break-risk warning. Show a strong warning only after a stable reading on the selected string has remained beyond its risk threshold for a defined interval; clear it predictably after correction/release. Chromatic mode may show any stable note; string mode must not compare an obviously different string against the selected target and immediately imply string tension risk. UI interpolation can smooth the needle, but must not decide pitch truth or warning timing.

Use the same Rust code path for synthetic tests and live capture; TypeScript handles only capture and presentation. Validate with synthetic tones/chirps, real isolated guitar plucks, quiet and loud attacks, note decay, neighboring strings, harmonics, standard and alternate tunings, and rapid mute/unmute. Record time-to-stable, false note changes, warning false positives, p95 processing time, and CPU; then run physical checks on iPhone Safari, iPad Safari, and desktop Chrome. The existing chord-recognition corpus does not validate tuner behavior. Keep documented regressions/rejected variants in `docs/AUDIO_EVALUATION.md`.

## Availability and release gates

Public: a fresh checkout and one-command container start must work without external accounts; practice/tuner should remain usable offline after first load. Private: exercise initial sign-in, paid access, offline grace, reconnect/outbox replay, sign-out, account switch, stale asset/version update, and provider failures. Set explicit behavior for denied/revoked microphone permission and audio interruption on Safari. Do not cache authenticated HTML as a reusable shell or silently replay one account's queued mutations under another account.

For each migrated slice, run Node 24, Poku, Biome, typecheck, boundary checks, and relevant browser visual/accessibility checks. Rust edits also require formatting, Clippy, native tests, and WASM parity. Before releasing the public package, inspect tarball contents and test a clean private install/build; then deploy and smoke-test hosted routes. Keep the alpha label until recognition and physical-device evidence meet the existing release criteria.
